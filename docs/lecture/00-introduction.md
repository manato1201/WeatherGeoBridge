# 第 0 回 天気を「判断」まで届ける仕組み(全体の見取り図)

> 所要時間の目安: 1 時間 / 前提: HTTP と JSON の基本

## この回のゴール

- 天気の取得 → キャッシュ → 画面・通知・**MCP(AI から呼ぶ口)**という、構成の流れを説明できる。
- **API キーをブラウザに出さない**構成(Next.js のサーバー側が中継する)の理由を説明できる。
- 「判断」(傘は要るか・洗濯物は外に出せるか)を、**ルールベースの純粋関数**にした理由を説明できる。

## 1. 構成

![WeatherGeoBridge の構成](../diagrams/architecture.svg)

| 場所 | 役割 | 技術 |
|---|---|---|
| `web/` | 画面(ダッシュボード・天気アトラスの地図)。**API キーを持つのは、このサーバー側だけ** | Next.js(Vercel) |
| `worker/` | 天気の取得・正規化・キャッシュ・通知・REST API | Cloudflare Workers(TypeScript)・KV |
| `mcp_server/` | AI(MCP クライアント)から呼ぶ口。**Worker の公開 API を呼ぶだけ**(ロジックを二重に持たない) | Python |

データ元は **Open-Meteo**。画面の下には、いつも「データ元・取得時刻・予報であって保証ではありません」を出します。

## 2. なぜ Next.js のサーバー側が間に入るのか

ブラウザの JavaScript は、利用者に**中身を見られます**。API キーをそこに置くと、誰でも盗めます。そこで、ブラウザ → **Next.js の API ルート**(サーバー側)→ Worker、と中継し、キーは**サーバー側の環境変数だけ**に置きます。Worker には `X-API-Key` ヘッダを付けて呼びます。

> 原則: 秘密は、**利用者の手元で動くコードに置かない**。

## 3. 判断をルールベースにする

「傘は要るか」は、AI に聞くと**遅く・ぶれ・説明できません**。ここでは、降水確率のしきい値で決める**単純なルール**にし、**根拠(evidence)**を一緒に返します。ルールは**外部通信をしない純粋関数**なので、境界値(降水確率 50% ちょうどなど)を単体テストで確かめられます(第 1 回)。

## 確認問題

1. API キーを、ブラウザの JavaScript に置かないのは、なぜですか。
2. MCP サーバーが、天気の取得ロジックを持たず、Worker を呼ぶだけなのは、なぜですか。

## 解答

1. 利用者が中身を見られるから(盗まれる)。サーバー側だけに置けば、ブラウザには出ない。
2. ロジックが**二重**になると、片方だけ直して食い違う。実際に動いている公開 API を呼べば、画面も MCP も**同じ結果**になる。

## まとめ

- 画面 → Next.js のサーバー側 → Worker(取得・キャッシュ・通知)。MCP も同じ Worker を呼ぶ。
- キーはサーバー側だけ。判断は、説明できる**ルールベースの純粋関数**。
- 次の回は、その判断ルールの中身。
